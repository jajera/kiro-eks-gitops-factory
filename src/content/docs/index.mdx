## Why the factory exists

<Still
  src="media/migration-to-eks-gitops.png"
  darkSrc="media/migration-to-eks-gitops-dark.png"
  alt="Diagram of migrating Docker, Podman, ECS, and VM hosts through a GitOps factory onto EKS, Kubernetes, Argo CD, Git, and ECR"
  caption="Existing runtimes converge through the factory onto one EKS and Argo CD GitOps path."
/>

At a few apps, a careful engineer can do that by hand. At hundreds of containers, across multiple
teams, it does not scale. Each person brings a slightly different layout, naming, and policy
choices. Reviews get slow, and the drift is hard to see because nobody wrote down one way to do
it.

Prompting a model harder does not fix it. A bare model invents a different tree for each app, and
given a shell it will apply that tree straight to a live cluster.

So the decisions move into the repository instead of into the prompt.{" "}
<Tooltip term="steering" label="Steering" /> carries the knowledge a reviewer would otherwise
supply from memory, a <Tooltip term="skill" label="skill" /> fixes the procedure into an ordered
sequence, <Tooltip term="hooks" label="hooks" /> refuse what must not happen no matter how the
request is phrased, and an <Tooltip term="agent" label="agent" /> bundles the three so one thin
prompt activates all of it.

**skills generate → hooks enforce → humans approve.** This page claims none of the three clauses
yet — it states the shape of the argument the rest of the site walks, and each page that follows
takes up the clause it can actually prove.
