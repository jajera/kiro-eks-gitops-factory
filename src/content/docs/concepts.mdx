## The path you already have

### EKS

<p>
  <Tooltip term="eks" label="Amazon EKS" /> is the managed Kubernetes control plane. This factory **assumes a cluster already exists**. Labs A–C do not create EKS; they shape app trees and prove policy offline so you are not inventing layout on a live API.
</p>

### Argo CD

<p>
  <Tooltip term="argo-cd" label="Argo CD" /> is the GitOps sync engine. Humans merge a PR; Argo syncs what landed in Git. The factory drafts manifests and Application wiring — it does not bypass review, and it does not `kubectl apply` from chat.
</p>

Together: **EKS runs workloads; Argo CD reconciles desired state from Git.** The factory makes
the Git side consistent so both stay predictable at scale.

## Policy offline before the cluster

### Gatekeeper

<p>
  <Tooltip term="gatekeeper" label="OPA Gatekeeper" /> is the in-cluster admission controller. Once installed, it evaluates <Tooltip term="constraint-template" label="ConstraintTemplates" /> against objects as they enter the API. Live Lab D (out of scope here) is where that webhook matters on a real cluster.
</p>

### gator

<p>
  <Tooltip term="gator" label="gator" /> is the **offline** Gatekeeper CLI. Lab A runs `gator verify` against constraint suites on your laptop — no cluster credentials, no webhook. That is why setup pins a gator version and why chart skew is called out separately: the CLI and the vendored Helm chart are related but not the same binary pin.
</p>

**Rule of thumb:** Gatekeeper enforces on the cluster; gator proves the same rules before the
cluster is in the loop. Which violations actually fail depends on each Constraint's
`enforcementAction` — see below.

### The constraint set

<p>
  Every rule below is a ConstraintTemplate under [`infrastructure/gatekeeper/constraint-templates/`](https://github.com/jajera/kiro-eks-argocd-migration/tree/main/infrastructure/gatekeeper/constraint-templates), each bound to a scope by a matching <Tooltip term="constraint" label="Constraint" />, each proven by a gator suite. Lab A walks the full chain for one of these (`httpsonly`); the rest follow the same pattern.
</p>

</p>

### Defined is not the same as enforced

<p>
  The table above is an **inventory of Rego checks**. Whether a violation actually fails is `spec.enforcementAction` on each <Tooltip term="constraint" label="Constraint" />:
</p>

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sHttpsOnly
metadata:
  name: ingress-https-only
spec:
  enforcementAction: deny # dryrun | deny
  match:
    kinds:
      - apiGroups: ["extensions", "networking.k8s.io"]
        kinds: ["Ingress"]
```

Under **`dryrun`**, Gatekeeper still evaluates the object and can record a violation — but it does
**not** reject admission, and app checks that run `gator test --deny-only` stay green. Nothing in
the PR path fails, so non-compliant manifests keep shipping. The bite comes later: the day you
flip the same field to **`deny`**, every accumulated violation starts blocking at once.

:::caution
If you are going to run Gatekeeper, introduce it **from the start** and ship constraints as
**`deny`** once the house pattern exists. Treat dryrun as a short observe window, not a steady
state — otherwise “green” CI only means deny-only gates passed, not that the inventory above is
clean.
:::

<p>
  This factory follows that stance for ready rules (including `httpsonly`): they ship as **`deny`**. The rare holdout is rules that need real account-specific values you do not have yet — notably <Tooltip term="wafv2" label="WAFv2" /> Web ACL ARNs — which stay **`dryrun`** until those ARNs exist. Lab A walks one Constraint end to end, including this field.
</p>

## How Kiro reaches context

### MCP

<p>
  <Tooltip term="mcp" label="MCP" /> (Model Context Protocol) is how <Tooltip term="kiro" label="Kiro" /> attaches tools and doc sources to a session. In this factory:
</p>

- **Docs MCP stays on** so the agent can read project guidance without inventing APIs.
- **Live cluster adapters stay off** until a human intentionally enables them — the Git-only hook
  story in Lab C depends on that boundary.

MCP is not something you install in setup for Labs A–C beyond what Kiro already ships. You will
see the config map in [Lab B](../lab-b/); you do not need a custom MCP server to start Lab A.
